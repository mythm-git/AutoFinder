# Architecture

## Canonical normalization boundary

After minimal identity extraction and persistent early deduplication, `ApifyKleinanzeigenNormalizer` maps raw Apify fields to the marketplace-independent `NormalizedListing` domain model. It preserves deep-copied raw source evidence, does not infer facts from title or description, and represents unavailable optional facts as `None` plus normalization warnings. `BasicDealFilter` receives only this canonical model; a future direct collector can supply the same contract without changing downstream business logic.

AutoFinder is code-first and Python-first. n8n later has a deliberately small boundary: start the local application, schedule it, and optionally monitor successful completion. It must not host business logic.

Python owns collection, raw-evidence preservation, normalization, early deduplication, deterministic filtering, AI orchestration, valuation inputs, canonical financial calculations, deal evaluation, logging, reporting, and application lifecycle.

`ApifyKleinanzeigenCollector` is the initial `ListingCollector` implementation. It receives `SearchConfig`, `CollectionConfig`, and `ApifyConfig`, sends only the verified actor payload fields `searchUrl` and `maxItems`, and returns `CollectionResult`/`RawMarketplaceListing` evidence. A future direct Kleinanzeigen collector can replace it without changing downstream consumers. In v0.1, the collector requests only the configured latest-listings limit (initially 5) and never searches deeper to replace later duplicates.

Apify/Kleinanzeigen results are acquisition evidence, not trusted business validation: later normalization and filters independently validate important conditions even if the configured search URL contains filters. Raw item mappings are retained intact.

`JsonSeenListingRepository` is the initial `SeenListingRepository` implementation. It stores only `marketplace`, external listing ID, and UTC `first_seen_at` under `data/state/seen_listings.json`; a database can replace it later behind the same contract. `EarlyDeduplicator` extracts identity from Apify's raw `id`, persists each valid unseen listing before later filters, and rejects historical, same-batch, or identity-less records. State writes use sibling temporary files followed by atomic replacement. Corrupted state fails closed and is never silently reset. V0.1 assumes one local runtime instance; locking can be strengthened later if needed.

`BasicDealFilter` accepts only normalized listings emitted after early deduplication. It independently checks configured canonical values even when the marketplace search URL includes the same limits, because external filter results are evidence rather than trusted enforcement. It returns stable rejection codes versus non-blocking warnings and never mutates preserved source evidence. Only passed listings will reach future AI work.

`AIManager` is the sole downstream AI entry point. It accepts a provider-neutral `StructuredAIRequest` with a Pydantic response model, invokes `GroqProvider` first, validates JSON locally, and invokes `GeminiProvider` only after classified retryable provider or response failures. `StructuredAIResult` records the successful provider/model, measured latency, available token metadata, safe response ID, and safe attempt summaries. Provider adapters never expose hidden reasoning or raw responses. See `AI_PROVIDERS.md`.

`VehicleAnalyzer` is the first consumer of this boundary. It accepts only a passed `NormalizedListing`, creates a minimal deterministic evidence packet, and requests the canonical `VehicleAnalysis` schema through `AIManager`; it never calls a provider SDK directly. Its response preserves normalized make/model/mileage/power in a dedicated `structured_source` section, keeps text-derived interpretation separate, and rejects an analysis that alters those source facts. The analysis separates current faults, completed repairs, maintenance, seller claims, positive signals, risks, and relevant missing information. It does not calculate monetary repairs, value, profit, ROI, or a candidate score. See `VEHICLE_ANALYSIS.md`.


`RepairEstimator` and `AIValuator` are independent `AIManager` consumers. Both accept only `NormalizedListing` plus validated upstream models; they do not reinterpret raw descriptions or bypass provider fallback. Repair items distinguish current required work, evidence-backed near-term maintenance, and bounded uncertainty reserve; Python verifies aggregate totals. Valuation is explicitly `AI_ESTIMATE`, not comparable-market evidence, and separates current as-is value from post-repair resale value without double-penalizing repaired faults. Neither service performs investment, profit, ROI, candidate, or alert logic. See `REPAIR_ESTIMATION.md` and `AI_VALUATION.md`.
